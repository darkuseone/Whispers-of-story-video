# ТЗ: удержание, шортсы, обложки, производство

Аудит конвейера на коммите `55341f7` + план работ по пунктам.
**Код по этому документу ещё не писан** — он для согласования.

Обозначения сложности: **Н** низкая (до полудня, одна функция),
**С** средняя (день-два, две-три функции + смоук), **В** высокая
(трогает раскладку таймлайна или формат кэша).

Каждый пункт помечен ценой рендера: **0** — считается по тайм-кодам и
тексту, ничего не стоит; **+ffmpeg** — добавляет фильтры в граф склейки;
**$** — тратит токены/деньги.

# ЧАСТЬ 1. АУДИТ ТЕКУЩЕЙ СБОРКИ

## 1.1 Последовательность прогона (`stage: auto`)

```
detect (workflow)
  ├─ push jobs/*.json (A)  → auto
  ├─ push .render/*.retry  → render      (кэш озвучки+материала)
  ├─ push .build/*.retry   → auto
  └─ push .shorts/*.retry  → shorts      (final.mp4 из релиза)

Этап 1  assets.py
  1. build_voice      ElevenLabs поблочно, посимвольный alignment
                      → block_NN.mp3 + block_NN.json + pause_NN.mp3 (2.0–3.0 с)
                      → voice_full.m4a (concat), marks.json, state.json
  2. build_images     xAI (Magnific выключен), пакетом или синхронно
  3. fetch_material   8 источников, playable() → trim_long_clip →
                      cap_clip_resolution (1080p), _manifest.json с запросом
  4. vet.vet_all      3 яруса: cheap_problems → critic (лапласиан) → зрение
  5. refill_after_vet если брака >40% — вторая волна + повторный vet
  6. fill_gaps        добор генерацией под оставшиеся дыры

Этап 2  build.py
  1. plan_shots         вступление кусками, тело по границам предложений
  2. set_render_durations  добавка на перекрытие xfade + PAD (2 кадра)
  3. render_one × N     ПАРАЛЛЕЛЬНО по числу ядер, каждый кадр → свой mp4
  4. join × ceil(N/12)  ПОСЛЕДОВАТЕЛЬНО, группами по 12 кадров
  5. concat_segments    -c copy
  6. build_audio        sidechain-дакинг + 2–3 подложки + ямы-события
  7. mux -shortest      + замеры хвоста, SRT, монтажный лист

Этап 3  youtube.py → описание, главы, covers.py (2 обложки xAI)
Этап 4  shorts.py  → 2 вертикальных ролика
```

## 1.2 Фильтр-граф одной группы склейки (`build.join`)

Это ядро рендера. Порядок фиксирован и каждый шаг там не случайно:

```
[k:v] lut3d=<семейный | архивный>          ← на КАЖДЫЙ из 12 входов, ДО склейки
   └─ xfade цепочкой: 11 переходов, offset = граница предложения
      └─ eq=saturation=0.90:contrast=0.98
         └─ curves (холодная растяжка теней: b 0.076 > r 0.038)
            └─ [опц.] scale+hflip оверлея → blend=all_mode=screen
               └─ [опц.] noise=alls=<grain>:allf=t+u
                  └─ [опц.] vignette=PI/max(st.vignette, 3.2)
                     └─ [первая группа] fade=t=in
                     └─ [последняя]     fade=t=out:d=6
                                        tpad=stop_duration=11:color=black
                        └─ drawtext × k  (плашки/титулы/THE END,
                                          drawbox для полноэкранной карточки)
                           └─ setsar=1
                              → libx264 crf 22 preset veryfast
```

**Где генерируются титры.** Всё в `pipeline/editorial/textcard.py`, всё
через `drawtext`, всё вклеивается в тот же граф склейки — отдельного
прохода нет и не нужно. Пять слоёв, один список `moments`:

| слой | функция | стиль | когда |
|---|---|---|---|
| название ролика | `opening_title` | `title` 92pt | пауза после первой фразы (`opening_at`) |
| титул главы | `chapter_titles` | `title` 52pt | `CHAPTER_LEAD = 1.9` с до первого слова главы |
| плашка-число | `moments` | 6 стилей | на датах/суммах в развязках |
| полноэкранная карточка | `interrupts` | `interrupt` | ≤4 на ролик, не чаще 1/8 мин |
| THE END | `the_end` | `title` 46pt | `anchor="tail"`, от конца последней группы |

**Переходы между сценами.** `xfade` внутри группы. На границе главы —
`st.pick_transition(chapter=True)`: случайный из
`["fadeblack","fadeslow","fade","dissolve","fadegrays","circleclose"]`,
1.6–2.8 с.

## 1.3 Узкие места по времени рендера

**Замер, который уже есть в репозитории** (`render.py`, шапка): zoompan —
31× реального времени, scale+crop — 2.6×. Отсюда считается остальное.

1. **Каждый кадр кодируется дважды.** `render_one` пишет отдельный mp4
   (crf 18, veryfast), `join` его тут же декодирует и кодирует заново
   (crf 22). На 40 минут это ~2400 секунд материала, прогнанных через
   x264 два раза. Первый проход нужен (разные источники, разные
   движения), но **crf 18 на промежуточном файле избыточен** — второй
   проход всё равно давит до 22.
2. **`join` идёт последовательно.** ~20–25 групп по 12 кадров; внутри
   каждой — 12 × `lut3d`, 11 × `xfade`, `curves`, `noise`, `vignette`.
   Это самый тяжёлый граф конвейера, и он крутится на одном процессе,
   пока `render_one` перед этим честно занимал все ядра. **Главный резерв
   ускорения.**
3. **`noise` и `vignette` — самые дорогие фильтры графа**, и оба
   постоянные на весь ролик. `noise=alls=N:allf=t+u` считает шум
   покадрово на полный кадр 1920×1080.
4. **`tmp/` не кэшируется.** В Actions сохраняется только
   `work/<id>/assets`. Значит `stage: render` заново рендерит ВСЕ кадры и
   ВСЕ группы — «пересборка монтажа» экономит только деньги, не время.
   Полностью кэшировать `tmp/` нельзя (десятки гигабайт при лимите 10 ГБ
   на репозиторий), но см. 5.2.
5. **`prepare_image` (Pillow, холст 3000 px) идёт внутри `render_one`** —
   то есть в потоках, где параллелизм даёт CPython GIL-овую пилу на
   декодировании JPEG. Мелочь на фоне x264, но бесплатно чинится.

Порядок величин: этап 2 на 40-минутном ролике — по комментариям в
workflow «монтаж уже съел 1–2 часа», при лимите джоба 330 минут.

## 1.4 Хрупкие места — где ломается тихо

Отсортировано по «насколько дорого обнаружить».

**(A) Переход последнего кадра каждой группы молча выбрасывается.**
Настоящий дефект, не гипотеза. `set_render_durations` даёт последнему
кадру группы `extra = 0.0`, а `join` крутит `for k in range(1,
len(group))` — то есть переход, записанный в `group[-1]["transition"]`,
не используется НИКОГДА. Группы сшиваются `concat -c copy`, встык.

Последствия:
- на 40-минутном ролике ~20 стыков из ~250 идут жёстким cut при
  `hard_cut_probability = 0.0` — то есть канал, у которого «резких
  склеек нет вовсе», раз в две минуты даёт резкую склейку;
- **граница главы, попавшая на кратный 12 кадр, теряет своё
  затемнение целиком.** Вероятность ~1/12 на главу, при 13–14 главах —
  примерно одна глава на ролик. Ровно та проблема, которую решает
  Часть 2.2, и решать её надо ВМЕСТЕ с ней.

Диагностики нет ни в логе, ни в `rails`, ни в смоуке.

**(B) Верхний уровень `jobs/*.json` не валидируется.** `style_override`
проверяется жёстко (`OVERRIDABLE`/`ENUMS`, неизвестный ключ роняет
сборку) — и это правильно. А вот верхний уровень принимает что угодно:
опечатка `footage_query` вместо `footage_queries`, `image_prompt`,
`vet_contexts`, `voice_setting` — молча даёт умолчание. Это тот же класс,
что уже стоил ролика (`similarity_boost` → `similarity`,
`vet_context` на `dead-internet-01`), просто ещё не закрытый.

**(C) `youtube.chapters` ищет главу по началу блока в субтитрах** —
после полного монтажа, на этапе 3. Смоук это дублирует бесплатно
(`youtube.chapters(job, cues)`), но только если смоук вообще прогнали.
Ловушка живая: `R.C.`, `U.S.`, `Gods?` уже роняли этап 3 после двух
часов рендера.

**(D) Тайм-коды и `final.mp4` расходятся при `mux -shortest`.** Ловится
замером в конце `build.main` — но замер только ПЕЧАТАЕТ предупреждение,
не роняет прогон. Ролик с обрезанным хвостом уедет в релиз с нулевым
кодом возврата.

**(E) `beds_for` молча теряет отсутствующие подложки** (лог есть, падения
нет). Правильное решение для последнего шага, но при опечатке в
`music` ролик выйдет вообще без музыки, и узнаешь об этом на просмотре.

**(F) У шортсов нет ни одной проверки.** `smoke.py` не трогает
`shorts.py` вовсе. Все дефекты оформления (ширина хука, шрифт, поля,
пустые окна) видны только глазами на готовом файле — а именно там их
больше всего, см. Часть 3.

## 1.5 Как сейчас подбирается материал под сцену

Двухступенчато, и обе ступени существуют:

**При скачивании** (`assets.py`): `relevance_score(query, tags)` —
взвешенное пересечение значимых слов запроса и тегов находки; длинное
слово (≥7 знаков) весит 3.0, короткое 2.0, плюс доля закрытого запроса.
`_best_by_relevance` берёт **n лучших**, а не n первых прошедших порог.
Плюс `script_grounded_queries` вытаскивает имена собственные из
`script_blocks` и добавляет их к запросам спецификации.

**При раскладке** (`build.ShotPicker.take`): у каждого файла есть слова —
у генерации из промпта, у стока/архива из запроса в `_manifest.json`. У
кадра есть текст предложений, звучащих под ним. Берётся файл с
наибольшим пересечением, при равенстве — позиция на таймлайне, с
износом за повторы (в том числе за показы в ПРОШЛЫХ роликах, из
`channel/log.json`, вес 0.5).

**Это не плоский рандом.** Смоук меряет процент попаданий и роняет
прогон при обвале (`floor = {"clip": 4.0}`, для остальных 12%).

Что здесь реально слабо:
- **мешок слов без синонимов и морфологии.** «guidestones» в запросе и
  «guide stones» в тегах — ноль пересечения. «monument» и «monuments» —
  ноль. Это чинится стеммингом за десять строк без единого запроса к
  модели;
- **порог у стока опущен до 4%** и это осознанно (иначе не выполняется
  доля видео), но означает, что клипы в теле часто ставятся «лучшим
  доступным», а не «подходящим»;
- у файлов без записи в манифесте слова берутся из имени файла —
  `clip_003_pexels` даёт слова «clip pexels».

# ЧАСТЬ 2. УДЕРЖАНИЕ В ОСНОВНОМ ВИДЕО

## 2.1 Открытие: хук → настоящая пауза → карточка названия

### 2.1.1 Динамика первых 5–10 секунд — сейчас лотерея. **С / 0**

**Что нашлось.** `opening` выпадает жребием из семи вариантов
(`cold_open`, `long_establish`, `quick_cuts`, `black_card`,
`slow_reveal`, `hard_in`, `starlit`), защита от повтора — только два
последних ролика. Три из семи ставят первым кадром ОДИН длинный план:
`starlit` 8–12 с, `slow_reveal` 6–9 с, `long_establish` 5.5–8.5 с.

То есть примерно в 40% выпусков **первые десять секунд — это один кадр**.
Ответ на вопрос «достаточно ли динамики»: у половины роликов да
(`quick_cuts` даёт куски по 0.9–2.4 с, `hard_in` и `cold_open` по 1.4–3.3),
у другой половины нет.

**Что делать.** Не выкидывать длинные открытия — они нужны как ось
разведения, — а **ввести пол по числу склеек в первые 10 секунд**:
не меньше трёх смен кадра, чем бы ни выпало открытие. Для `first_long`
это значит резать длинный первый план на 2–3 куска ОДНОГО файла через
`ClipCutter.take_start` (механизм уже есть) — план остаётся
«установочным», но дышит.

**Механизм:** новое поле `op["min_cuts_10s"] = 3` в `opening_plan`,
проверка после раскладки вступления, добор нарезкой. Плюс правило в
`rails.audit` — «в первые 10 с меньше трёх кадров» как замечание.

**Риск по рендеру:** ноль, число кадров меняется на два-три.

### 2.1.2 Настоящая пауза диктора перед карточкой. **С / 0**

**Что нашлось — и это главное расхождение с ТЗ.** Карточки названия
сейчас ставится на `marks[0]["end"] + 0.35` — то есть через треть
секунды после конца первой фразы. **Но паузы там нет.** Паузы
(`pause_NN.mp3`, 2.0–3.0 с) конвейер вставляет только МЕЖДУ БЛОКАМИ
сценария. Внутри блока 1 диктор говорит непрерывно: первая фраза
кончилась — вторая началась. Карточка выезжает поверх продолжающейся речи.

Заказанное «после хука пауза 2–3 с, синхронно с карточкой, потом диктор
продолжает» **в конвейере не реализовано вообще.**

**Механизм — бесплатный, без переозвучки.** `block_01.mp3` уже лежит на
диске, `block_01.json` даёт посимвольные тайм-коды, конец первой фразы
известен до миллисекунды. Значит:

1. в `build_voice`, после получения alignment блока 1, резать
   `block_01.mp3` по концу первой фразы (`ffmpeg -ss/-to`, потоковое
   копирование), вставлять между кусками `_silence_mp3(HOOK_PAUSE)`;
2. `HOOK_PAUSE = 2.4` по умолчанию, поле `hook_pause` в спецификации,
   диапазон 0 (выключить) … 4.0;
3. все `marks` блока 1 после этой границы и **все последующие блоки**
   сдвинуть на `+HOOK_PAUSE` (это уже делается арифметикой `offset`,
   надо только добавить слагаемое);
4. `textcard.opening_at` меняется на «начало паузы + 0.25», а
   `OPENING_HOLD` подрезается под длину паузы, чтобы титр ушёл до
   первого слова второй фразы.

**Важно:** это правка ЭТАПА 1, а не монтажа. Первый прогон после
внедрения обязан пересобрать `voice_full.m4a` и `marks.json` — но **не
переозвучивать**: блоки в кэше, режется уже оплаченное.

**Риски.** Сдвиг таймлайна на 2.4 с проверяется теми же замерами, что
уже есть (`таймлайн разошёлся со звуком`). Тонкое место — `shorts.py`
и `youtube.chapters` читают `marks.json`, и он будет верный, если
сдвиг сделан в `build_voice`, а не постфактум.

**Сложность С**, потому что трогает границу «озвучка/монтаж» и требует
инвалидации `voice_full.m4a` при смене `hook_pause` (по образцу
`_voice_meta.json`).

### 2.1.3 Кегль и вес карточки названия. **Н / 0**

Сейчас: Montserrat **Regular**, 92 pt, разрядка пробелами по словам,
ужимается под 80% ширины кадра (`TITLE_FILL`), тень без обводки.

Заказано «увеличить кегль / сделать тоньше». Оба разумны и не спорят
друг с другом — тонкое начертание при большем кегле читается лучше, чем
среднее при меньшем.

**Предложение:** `OPENING_SIZE 92 → 108`, `TITLE_FILL 0.80 → 0.84`,
шрифт вернуть на **Montserrat-Light** (файл уже лежит в
`assets/fonts/`, он и был первым выбором до правки «чуть пожирнее»).
Тень при Light поднять с `black@0.55` до `black@0.68` и добавить
`shadowx=1` — Light без этого теряется на ярком архивном кадре, из-за
чего его и меняли.

**Проверять только рендером.** Читать код тут бесполезно, это ровно тот
класс правок, где видно глазами на кадре.

**Риск:** длинные названия. `_fit_size` уже ужимает под ширину, но при
108 pt ужиматься будет чаще — то есть разброс кеглей между выпусками
вырастет. Лечится потолком снизу (`floor` в `_fit_size` поднять с 22 до 56).

## 2.2 Главы: затемнение + карточка

### 2.2.1 Гарантированное затемнение на каждой границе. **С / +ffmpeg**

**Что сейчас.** Граница главы получает случайный переход из шести, и
только два из них (`fadeblack`, `fadegrays`) реально уходят в тёмное.
То есть **затемнение бывает примерно на трети границ**. Плюс дефект (A)
из аудита: каждая двенадцатая граница теряет переход вообще.

**Что делать.**

1. **Сначала починить (A)** — иначе любое правило про границы глав будет
   работать «почти всегда». Два варианта:
   - *дешёвый:* при раскладке не позволять границе главы вставать на
     последний кадр группы — сдвигать разбиение на группы, а не кадры
     (`SEG_SIZE` перестаёт быть константой, группы становятся 11–13
     кадров). Ничего не стоит, ломает мало;
   - *честный:* переносить переход последнего кадра группы в НАЧАЛО
     следующей (`xfade` первого кадра со «хвостом» предыдущей группы).
     Дороже, требует запаса в рендере предыдущей группы и ломает
     `concat -c copy`. **Не рекомендую.**

   Рекомендация — дешёвый вариант плюс проверка в `rails`.

2. **Зафиксировать чёрный переход на границе главы:**
   `CHAPTER_TRANSITIONS = ["fadeblack"]` плюс `fadegrays` для разнообразия
   раз в три-четыре главы. Длительность 1.6–2.8 с уже заказанная «1–2
   секунды затемнения» с запасом.

3. **Дать чёрному подержаться.** `xfade=fadeblack` уходит в чёрное и
   выходит из него ВНУТРИ своей длительности — паузы на чёрном нет.
   Если нужна именно пауза (а под карточку главы она и нужна), делать
   так: последний кадр перед границей получает
   `fade=t=out:st=<конец>-0.8:d=0.8`, первый кадр после —
   `fade=t=in:st=0:d=0.8`, а между ними обычный короткий `xfade`. Это
   даёт «провал в чёрное на ~0.6 с», и карточка главы садится ровно туда.

**Цена рендера:** два `fade` на кадр × 13 глав — на фоне `noise` это
ноль.

**Риск:** `fade` ставится ПОСЛЕ `lut3d`, иначе чёрное не чёрное (эта
грабля уже описана в `join` для `first`). Ставить надо в per-input
цепочку, не в общий пост.

### 2.2.2 Стиль карточки главы отличать сильнее. **Н / 0**

Сейчас: тот же шрифт, `center`, 52 pt против 92 у названия ролика.
Отличаются только кеглем и положением по вертикали.

Заказано «визуально отличаться, тем же шрифтом». Предложение —
разводить по **трём** осям сразу, чтобы отличие читалось за полсекунды:

| | название ролика | титул главы |
|---|---|---|
| кегль | 108 | 54 |
| вес | Montserrat **Light** | Montserrat **Regular** |
| положение | `center_high` (0.40 H) | `center` |
| разрядка | широкая (как сейчас) | **вдвое уже** |
| добавка | — | тонкая линия под текстом, `drawbox` 2 px, шириной в текст |

Линия под титулом главы — это `underline_wipe` без анимации, механизм
уже написан (см. `_one`, стиль `underline_wipe`); нужно только
разрешить `title` носить статичное подчёркивание.

**Риск:** `drawbox` требует `iw/ih` вместо `W/H` — грабля уже поймана и
описана в коде, повторить её легко.

### 2.2.3 Номер главы. **Н / 0**

Дешёвое усиление ориентации: над названием главы мелко «CHAPTER 4 OF 13»
(тем же Montserrat, 26 pt, `fontcolor=0xF2EFE9@0.55`). В сорокапятиминутном
ролике это ровно то, чего зрителю не хватает — «сколько ещё».
Данные уже есть: `chapter_edges` знает номер блока, `youtube.chapters`
знает общее число.

## 2.3 Финал: два варианта

Сейчас: `fade=t=out:d=6` на последней группе + `tpad` 11 секунд чёрного,
из них 1.2–5.2 занимает THE END, остальное — тишина.

### Вариант A — fade-to-dark-card (то, что есть, с доводкой)

Кадр гаснет 6 секунд, дальше чёрное поле, THE END, тишина.

- **цена:** ноль. `fade` и `tpad` — это два фильтра на последней группе;
- **плюс:** уже работает, проверен замером (`vd < total + tail_hold`);
- **минус:** последние 6 секунд картинки — это уход в НИЧТО, зритель не
  видит финального образа. Для формата «уснуть» правильно, для
  «досмотреть до конца и кликнуть следующий» — нет.

### Вариант B — freeze + darken

Последний кадр замирает и медленно темнеет ~5 секунд, THE END поверх
замершего кадра, потом чёрное.

- **механизм:** `tpad=stop_mode=clone:stop_duration=5` (клонирует
  последний кадр вместо чёрного) + `fade=t=out` поверх клонированного
  участка + второй `tpad` уже с `color=black` под тишину;
- **цена:** `stop_mode=clone` дороже `add` ровно на кодирование пяти
  секунд почти статичного кадра — то есть на 40-минутном ролике **менее
  0.2% времени рендера**. Практически бесплатно;
- **плюс:** финальный образ остаётся на экране, THE END ложится на
  картинку, а не в пустоту. Работает как маленькая обложка «конца»;
- **минус:** замерший кадр после 45 минут движения читается как
  «видео зависло» — на первые полсекунды, пока не начнётся затемнение.
  Лечится тем, что затемнение стартует сразу, без паузы.

### Рекомендация

**Гибрид, и он дешевле обоих по коду.** Оставить существующий `fade`, но
сделать его не «в чёрное», а **в тёмную стоп-кадровую карточку**:

```
последняя группа
  └─ tpad=stop_mode=clone:stop_duration=5      ← кадр замирает
     └─ fade=t=out:st=<конец−5>:d=5            ← и одновременно темнеет
        └─ tpad=stop_mode=add:stop_duration=<tail_hold>:color=black
           └─ drawtext THE END на границе      ← anchor="tail" уже умеет
```

Порядок именно такой: сначала клон, потом затемнение поверх него, потом
чёрный хвост. THE END встаёт на стык — половину времени он на угасающем
кадре, половину на чёрном, что и есть заказанное «как будто зритель
уснул».

**Сложность Н** (три строки в `join`), **риск средний**: `tpad`
дважды подряд в одной цепочке надо проверить замером длины — тот самый
случай, где `-shortest` молча всё срежет. Проверка уже написана
(`if st.tail_hold > 0 and vd < total + st.tail_hold - 0.5`), её надо
только расширить на +5 секунд стоп-кадра.

## 2.4 Сквозные текстовые акценты по ключевым фразам

Самый большой новый механизм в этом ТЗ. Разбиваю на «откуда брать
фразы» и «как рисовать».

### 2.4.1 Откуда брать привязку к тайм-кодам. **С / 0**

**Данные уже есть и уже точные.** ElevenLabs отдаёт ПОСИМВОЛЬНЫЕ
тайм-коды, они лежат в `work/<id>/assets/voice/block_NN.json`. Функция
`words_from_alignment` (сейчас живёт в `shorts.py`) собирает из них
слова с точностью до миллисекунды, включая правильный учёт пауз между
главами. **Ничего изобретать не надо — надо вынести её в общий модуль.**

Три источника ключевых фраз, по убыванию надёжности:

1. **Явная разметка в спецификации** — новое поле `accents` в
   `jobs/*.json`:
   ```
   "accents": [
     {"say": "nineteen eighty-three", "show": "1983"},
     {"say": "page 25",               "show": "PAGE 25"},
     {"say": "Hemi-Sync"}
   ]
   ```
   `say` ищется в словах начитки (нормализованное сравнение), `show` —
   что вывести; нет `show` — выводится `say` заглавными. Это главный
   путь: сценарист знает, что в его тексте ударное, а робот нет.
2. **Автоподбор через `textcard._phrase_at`** — уже написан, вытаскивает
   даты, эпохи, суммы, столетия. Сейчас его результат идёт только в
   угловые плашки на долях-развязках; для акцентов надо разрешить его на
   всех долях, но с более жёстким прореживанием.
3. **Имена собственные из `script_grounded_queries`** — механизм есть,
   применяется сейчас только к поисковым запросам.

**Прореживание — обязательное условие, а не пожелание.** Плотность:
не чаще одного акцента на 40 секунд, не больше 45 на сорокаминутный
ролик, и **ни одного в первые 30 секунд** (там уже название ролика) и
за 60 секунд до конца (там THE END). Ось `text_density` из вектора стиля
переиспользовать как множитель — тогда акценты автоматически разводятся
между выпусками, как всё остальное.

### 2.4.2 Как рисовать. **С / +ffmpeg**

Заказано: на футаже — мелко в углу, на статичной картинке — крупнее,
можно столбиком, мягкое появление.

**Механизм:** новый стиль `accent` в `textcard._one`, три раскладки.

```
кадр kind=clip   → место lower_right, кегль 34, одна строка,
                   fontcolor=0xF2EFE9@0.80, тень без обводки
кадр kind=image  → место upper_left,  кегль 52, до трёх строк столбиком
                   (перенос по словам, \n внутри одного drawtext НЕ
                    работает — нужен drawtext на строку, как в typewriter)
кадр в развязке  → существующая полноэкранная карточка, не трогаем
```

**Знание, какой под акцентом кадр, у нас есть**: `plan_shots` уже
разложил `shots` с полем `kind`, и `moments` считаются ПОСЛЕ плана
(`build.main`, порядок вызовов). То есть выбор раскладки — это поиск
кадра, накрывающего секунду акцента, одной строкой.

**Мягкое появление** — уже есть в `_one`: альфа с `fade_in`/`fade_out`
по выражению времени. Для акцентов взять `fade_in=0.55`, `fade_out=0.7`
и добавить **микро-сдвиг**: `y` уезжает на 12 px вверх за первые 0.5 с
(механизм `slide_up`, только амплитуда втрое меньше — 52 px там сделаны
под удар, здесь нужна не заметная глазу подача).

**Обязательное правило раскладки:** акцент не имеет права встать туда,
где в эту же секунду стоит титул главы, полноэкранная карточка или
плашка-число. Все они уже живут одним списком `moments`, значит проверка
пересечения по времени — цикл на десять строк перед сортировкой.

**Цена рендера.** Один `drawtext` на кадр — это доли процента. Но:
45 акцентов на ролик разложатся по 20–25 группам, то есть **+2–3
`drawtext` на группу**, и это поверх уже существующих. Каждый `drawtext`
с выражением по времени (`alpha='if(lt(t,...))'`) считается покадрово.
Замер до внедрения обязателен — **прогнать одну группу с 5 drawtext и
без, сравнить время.** Ожидание: +3–6% к времени склейки; если выйдет
больше 15% — резать плотность, а не отказываться от приёма.

### 2.4.3 Что НЕ делать

- **не выводить всю речь субтитрами.** Уже записано в
  `docs/улучшения-удержание.md` как сознательное решение, и оно верное:
  на 40-минутной документалке вшитые капшены превращают кадр в бегущую
  строку. `subs.srt` отдаётся YouTube отдельно;
- не ставить акценты в первые 30 секунд — там работает правило
  «только настоящий материал» и название ролика;
- не привязываться к `script_blocks` по индексу символа. Привязка
  только через посимвольный alignment: TTS растягивает и сжимает текст
  неравномерно, и «сороковое слово» звучит не на сороковой доле блока.

## 2.5 Kinetic-въезд текста: ffmpeg-эквивалент и стоит ли он того

Референс (`kinetic-center-build`): слова въезжают со scale + blur и
собираются по центру.

**Что из этого воспроизводимо в ffmpeg и почём:**

| приём | механизм | цена | вердикт |
|---|---|---|---|
| плавное появление по альфе | `alpha='if(...)'` в `drawtext` | ~0 | **уже есть**, работает |
| въезд по позиции | `y='<цель>+K*max(0,1-(t-t0)/D)'` | ~0 | **есть** (`slide_up`), надо только мягче |
| пословная сборка | по `drawtext` на слово, свой `t0` у каждого | ~0 | **дёшево и стоит делать** |
| **анимация кегля** | у `drawtext` `fontsize` **не анимируется** | — | **невозможно** без второго прохода |
| **blur на входе** | `gblur` красит ВЕСЬ кадр, не текст | дорого | **невозможно** без alpha-слоя |

**Про кегль и blur — это принципиальное ограничение, а не лень.**
В `drawtext` `fontsize` — константа фильтра, выражения по времени она не
принимает (в отличие от `x`, `y`, `alpha`). Чтобы анимировать размер и
размывать только текст, нужно рисовать титр **отдельным слоем с
альфа-каналом** и накладывать `overlay`:

```
color=black@0:s=1920x1080,format=rgba
  → drawtext (текст на прозрачном)
    → scale=eval=frame (анимация размера)
      → gblur=sigma='max(0,6-12*(t-t0))'  (размытие только слоя)
        → overlay поверх кадра
```

**Цена этого честная и высокая.** Второй полноразмерный RGBA-поток
1920×1080@30, `gblur` покадрово по нему, `overlay` с альфой. По классу
это ближе к `zoompan` (31× realtime), чем к `drawtext` (~0). На
сорокаминутном ролике включать такое НА ВЕСЬ таймлайн нельзя.

### Рекомендация

**Два уровня, и второй — только на трёх титрах ролика.**

1. **Везде (акценты, плашки, титулы глав): «мягкий въезд без scale».**
   Пословная сборка + альфа + сдвиг на 12–18 px. Слова появляются по
   одному с шагом 0.12 с, каждое проявляется 0.35 с и подъезжает. Это
   даёт **80% ощущения референса за 0% цены** — принцип «текст
   собирается», а не «текст возник», сохраняется полностью.
   Механизм — тот же `typewriter` из `_one`, но слоями по СЛОВАМ, а не
   по символам, и с альфой у каждого слоя своей.

2. **Только для карточки названия ролика (одна на выпуск, ~6 секунд):**
   полный alpha-слой со `scale=eval=frame` и `gblur`. Шесть секунд из
   2400 — это **0.25% таймлайна**, то есть при цене даже 30× realtime
   добавка к рендеру ~3 минуты на ролик. Приемлемо ровно потому, что
   это один титр.

   Для карточек глав (13 штук × 5 секунд = 65 секунд = 2.7% таймлайна)
   **не рекомендую**: +30 минут рендера за эффект, который на границе
   главы и так подан затемнением.

**Сложность В** для пункта 2 (новый вход в граф склейки, альфа-слой,
взаимодействие с `xfade`-цепочкой), **С** для пункта 1.

**Порядок работ:** сначала 1 (дёшево, покрывает все титры), потом
замерить, и только потом решать про 2.

## 3.1 Как они собираются сейчас

```
pick_windows   окно 1 = первые фразы ролика (роль hook)
               окно 2 = доля revelation с максимальным признаком «num»
               (или escalation с «turn»), окна не пересекаются
               длина 28–90 с, цель 62 с, границы = целые предложения

cut_plan       перерезка окна кусками 2.8–4.8 с; исходник выбирается
               по пересечению слов начитки со словами файла (+бонус
               кадру, стоящему на этом месте в длинном ролике)

render_cut     клип  → блюр-подложка + вписанный передний план (fit)
               фото  → статичный кадр, кроп 9:16 со смещением 0.38

write_ass      3 слоя: Question (жёлтый Archivo Black наверху, первые
               0.85 с крупно, потом уезжает наверх одним \move+\t),
               Caption (Montserrat ExtraBold, целые предложения, \an2
               снизу), Cta (последние 2.4 с)

звук           вырезка из final.mp4 (со сведением), afade на 0.4 с
```

Оформление сделано аккуратно — шрифты из репозитория, `fontsdir`,
безопасные зоны, замер ширины настоящим шрифтом. Проблема не в
оформлении.

## 3.2 Почему они выходят посредственными

**(1) Темп вдвое медленнее, чем нужно Shorts.** Кадр 2.8–4.8 с на
60-секундном вертикальном ролике — это 13–20 склеек. Формат живёт на
1.2–2.2 с. Причём правило «без Ken Burns» верное для длинного ролика, но
в шортсе оно означает **статичное фото на 4 секунды** — на телефоне это
вечность. И `CUT_MERGED_MAX = 7.0` позволяет слить два куска одного
файла в СЕМЬ секунд одного кадра.

**(2) Окно «hook» — это буквально начало ролика, целиком.** 62 секунды
подряд с первой фразы. Начало длинного ролика написано как медленный
холодный крючок под 40-минутный формат: «Я пересматривал запись… Четыре
утра, шестое июля». Для длинного это правильно, для Shorts — это минута
разгона без единого поворота. **Шортс должен быть смонтирован, а не
вырезан.**

**(3) Половина кадра пустая.** Горизонтальный сток вписывается по
ширине (`scale=SW:-2:decrease`), значит на кадре 1080×1920 видео
занимает 1080×608 — **треть высоты**, остальное блюр-подложка. Решение
защищает от тряски (и обосновано в комментарии), но платит за это
двумя третями экрана.

**(4) Субтитры целыми предложениями до 4 строк.** Осознанный уход от
караоке — правильный по причине (пословные тайм-коды плыли), но
результат: блок из 3–4 строк, висящий 5–6 секунд. Формат читает 1–2
строки по 2–3 слова, меняющиеся раз в 0.8 с. **И пословные тайм-коды у
нас точные** — `words_from_alignment` даёт миллисекунды, «плыли» они
из-за неучтённых пауз между главами, а это уже починено в той же
функции.

**(5) Первые 0.85 секунды.** Хук показывается крупно `HOOK_HOLD = 0.85`
с и уезжает. Это **меньше, чем зритель успевает прочитать три строки
текста**. Норма для Shorts — держать хук 1.5–2.0 с.

**(6) Конец — «FULL STORY ON THE CHANNEL».** Это не призыв, это
указатель. Ни петли, ни вопроса, ни причины остаться.

**(7) Нечего проверить.** `smoke.py` шортсы не трогает.

## 3.3 Что делать — по пунктам

### 3.3.1 Темп: 1.4–2.4 с, с ускорением к развязке. **Н / 0**

`CUT_RANGE = (2.8, 4.8)` → `(1.4, 2.4)`, `CUT_MERGED_MAX = 7.0` → `3.2`.

Плюс **кривая темпа внутри шортса**: первые 8 секунд по 1.2–1.8 с
(хук должен ощущаться быстрым), середина 1.8–2.4, последние 10 секунд
снова 1.3–1.8 (разгон к ответу). Это три строки в `cut_plan` —
множитель от `(t - t0) / (t1 - t0)`.

**Риск:** при 60 секундах и кадре 1.8 с нужно ~33 куска, а пул кадров в
окне — это то, что попало в `shots` на этом отрезке (~5–8 разных
файлов). Значит **повторов станет больше**. Лечится тем же
`ClipCutter`, что и в длинном ролике: брать РАЗНЫЕ куски одного файла
(механизм есть, `shorts.py` им не пользуется вовсе — берёт
`src_start` из плана длинного ролика и всё).

### 3.3.2 Вернуть движение — но в шортс, а не в длинный ролик. **С / +ffmpeg**

Правило «без Ken Burns» было принято из-за тряски при жёстком кропе.
Тряски больше нет (кроп заменён на fit+блюр). Значит запрет потерял
причину — **для фото**.

Предложение: **фото в шортсе получает медленный наезд 1.00 → 1.06 за
длину куска** (тот же `scale=eval=frame`+`crop`, что в `render.py`, а не
`zoompan`). Клип не трогать — у него движение своё.

**Цена:** фото в шортсе сейчас рендерится как `-loop 1` из готового
JPEG — практически бесплатно. С наездом станет как обычный кадр
длинного ролика, то есть ~2.6× realtime на 1080×1920. На 60 секунд
шортса, из которых половина фото, это +80 секунд рендера. **Приемлемо.**

### 3.3.3 Раскладка кадра: перестать терять две трети экрана. **С / +ffmpeg**

Три варианта, по возрастанию сложности:

- **A. Умеренный кроп + fit.** Не `fit` целиком и не `crop` целиком, а
  масштаб между ними: увеличить клип так, чтобы он занимал **70% высоты**
  вместо 32%, обрезав по бокам ~35% ширины. Тряска усиливается в 1.5×,
  а не в 3×. Одна строка (`scale=SW*1.5:-2` → `crop`).
- **B. Кроп с центром по движению.** Считать «где в кадре происходит
  движение» одним проходом `ffmpeg -vf select` и центрировать кроп туда.
  Дорого, ненадёжно на архивном материале. **Не рекомендую.**
- **C. Блюр-подложка остаётся, но верхнюю треть занимает не блюр, а
  текст.** То есть перестать считать блюр «потерей»: хук наверху и
  субтитры внизу как раз стоят на этих полях. Тогда 70% высоты под
  видео и не нужно.

**Рекомендация: A + C вместе.** Поднять клип до ~55–60% высоты (кроп по
бокам 20%), верхнее и нижнее поле оставить под текст. Кадр перестаёт
быть «маленьким видео в рамке» и становится вертикальной раскладкой.

### 3.3.4 Субтитры: 1–2 строки, смена по фразам. **С / 0**

Не возвращаться к караоке по одному слову — вернуться к **смысловым
кускам по 3–5 слов**, нарезанным из ПОСЛОВНЫХ тайм-кодов
(`words_from_alignment` уже даёт их точно, вместе с паузами).
`CAPTION_LINE = 26` оставить, `CAPTION_MAX_LINES = 4` → `2`.

Правило нарезки: копить слова, пока не наберётся 3–5 или не встретится
пауза >0.35 с, — тогда закрывать кусок. Пауза как разделитель важнее
числа слов: она совпадает с дыханием диктора.

**Плюс подсветка ключевого слова.** У ASS это `{\c&H00D4FF&}` внутри
события — то есть **ключевое слово в субтитре жёлтым, тем же
`#FFD400`**, что хук и обложки. Список ключевых слов — те же `accents`
из 2.4.1. Стоит ноль, узнаваемость канала растёт.

### 3.3.5 Хук: держать дольше и добавить причину. **Н / 0**

- `HOOK_HOLD = 0.85` → `1.7`, `HOOK_SHRINK = 0.65` → `0.5`;
- **вопрос обязан быть вопросом.** Сейчас при пустом
  `youtube.shorts_questions` вопрос собирается из первого предложения
  окна отрезанием по запятой и приклеиванием «?». Это даёт
  «I had watched the footage more times than I can count?» — то есть
  мусор. Правило: **если `shorts_questions` не задан — валить смоук**,
  а не выдумывать. Два вопроса на ролик пишет сценарист, это одна
  строчка в спецификации;
- **добавить обратный отсчёт-обещание.** На секунде ~3 мелкой строкой
  под хуком: «ANSWER AT 0:47» (или просто «WAIT FOR IT» — нет, это в
  `BANNED_HOOKS`, и правильно). Формулировка — «THE ANSWER IS AT THE
  END», один раз, 2.5 секунды. Это классический open-loop, и он не
  кликбейт: ответ в шортсе действительно есть.

### 3.3.6 Окна: монтировать, а не вырезать. **В / 0**

Самая большая правка и самая заметная по результату.

Вместо «62 секунды подряд с первой фразы» — **склейка из 2–3 кусков
разных мест ролика**:

```
шортс 1 (хук):
  0–6 с    первые 1–2 предложения ролика       (крючок)
  6–14 с   САМАЯ сильная фраза из revelation    (обещание, без ответа)
  14–55 с  продолжение вступления              (развязка обещания)

шортс 2 (развязка):
  0–5 с    вопрос из escalation                 (постановка)
  5–50 с   доля revelation целиком              (ответ)
```

Технически это просто **список окон вместо одного окна**: `render_short`
уже режет по `cut_plan` и клеит `concat`, звук берётся из `final.mp4`
по `-ss/-t`. Для нескольких кусков нужен второй проход по звуку
(вырезать 2–3 отрезка и склеить) — `ffmpeg -filter_complex concat` с
короткими `acrossfade` 0.15 с на стыках, чтобы не щёлкало.

**Риск:** субтитры и `words` считаются от одного `t0`. При склейке
кусков нужно вести собственный таймлайн шортса и пересчитывать в него
каждую реплику. Это и делает пункт «В» по сложности.

**Проверять смоуком:** сумма длин кусков = длине готового файла,
±0.1 с. Ровно та же логика, что уже стоит в конце `build.main`.

### 3.3.7 Юмор / интрига в первых секундах

Заказано «придумай сам». Честный ответ: **юмор этому каналу
противопоказан** — тон заявлен как «спокойное вечернее документальное
расследование», и шутка в первые секунды шортса обещает совсем другой
ролик, чем тот, на который ведёт. Отвал будет не на шортсе, а на длинном
видео, и это хуже.

Работающая замена интриги, всё бесплатно и всё из уже имеющихся данных:

1. **Конкретное число в первом кадре.** Не «древняя тайна», а
   «ЧЕТЫРЕ УТРА, 6 ИЮЛЯ 2022». `_phrase_at` уже умеет вытаскивать даты
   и суммы — взять самую «цифровую» фразу окна и поставить её первым
   акцентом.
2. **Документ на экране в первые 2 секунды.** В пуле почти всегда есть
   архивный скан / страница отчёта. Правило: **первый кадр шортса —
   `kind=arch`, если такой есть в окне.** Настоящий документ читается
   как «это не нейросеть» мгновенно.
3. **Оборванная фраза.** Хук-вопрос заканчивается многоточием, а не
   вопросительным знаком, когда в тексте окна есть незакрытый поворот.
4. **Петля.** Последний кадр шортса = первый кадр шортса. У YouTube
   Shorts автоповтор, и совпадение первого и последнего кадра даёт
   бесшовный луп — это чистая прибавка к просмотрам без единой новой
   идеи. Стоит: один лишний `render_cut`.

### 3.3.8 Смоук для шортсов. **С / 0**

Сейчас их не проверяет никто. Минимум:

- окна не пересекаются, каждое ≥ `MIN_LEN`, сумма кусков = длине файла;
- `shorts_questions` заданы и это вопросы (кончаются на `?`);
- хук после `wrap_question` укладывается в `QUESTION_MAX_LINES`;
- `hook_scale` в диапазоне 100–210 (за пределами — замер ширины сломан,
  та самая грабля с `\N`);
- шрифты на месте в `assets/fonts`;
- субтитры не наезжают на CTA.

Всё считается по `marks.json` и тексту, без рендера.

# ЧАСТЬ 4. ОБЛОЖКИ — ПРОМПТ-ИНЖИНИРИНГ

**Статус: сделано и лежит в `pipeline/covers.py`.** Структура не менялась:
модель по-прежнему рисует кадр вместе с жёлтым текстом, наложение и
`paint_hook` работают как работали, `youtube.py` вызывает `covers` тем же
способом. Изменился только текст промптов — и три вещи вокруг них,
которые без правки делали бы новый промпт бесполезным.

## 4.1 Что было не так с прежним промптом

Прежний `SCENE_LOCK` был написан по CTR-исследованию — то есть отвечал на
вопрос «какой кадр кликает». Он не отвечал на второй вопрос: **как
заставить диффузионную модель этот кадр нарисовать.** Четыре механических
дефекта, все измерены не нами (источники — в `docs/протокол-обложки.md`):

1. **Отрицания не работают.** «No logos, arrows, circles, starbursts,
   watermarks, YouTube UI» модель читает как перечисление того, что надо
   нарисовать: кросс-внимание остаётся на токенах самого понятия, а
   инструкция запрета почти не влияет на эмбеддинг. Половина прежнего
   промпта состояла из таких строк.
2. **«Photoreal cinematic still» — это переключатель в глянец.**
   Слова качества (`photorealistic`, `8k`, `masterpiece`, а в 2026-м и
   `cinematic`) включают «эстетический режим»: ровный свет, симметрия,
   пластиковые поверхности. Признак AI-картинки сегодня — не низкое
   разрешение, а то, что она слишком чистая. То есть промпт просил
   ровно то, от чего протокол обложек велит уходить.
3. **«Leave the largest empty region (top OR side)» — конструкция с
   „или“**, которую модель не разбирает. Зона под текст плавала от
   выпуска к выпуску, хотя `paint_hook` кладёт буквы **только наверх**
   (`y = H*0.07`). То есть кадр и запасной путь противоречили друг другу.
4. **«Readable at 120 pixels» модель проверить не умеет.** Требование
   надо переводить на язык, который она исполняет: «картинка
   разваливается на три-четыре крупных тональных пятна», «силуэт не
   разрывается на фоне», «читается в градациях серого».

## 4.2 Что стало

| было | стало |
|---|---|
| запреты списком «no X» | утверждения: «каждая поверхность, способная нести надпись, пуста или отвёрнута»; короткий хвост `Avoid` оставлен последним как слабая подстраховка |
| `photoreal cinematic still` | описание **захвата**: зерно, халация, виньетка, хроматика на контрастном крае, плоскость пыли в свете |
| света нет вовсе | **план света внутри каждого паттерна**: один мотивированный ключ, направление, жёсткость, заполнение, поведение теней |
| палитра словами | палитра **системой**: два цвета, hex фона (`#0B1220`–`#161C28`) + тёплый предмет; тёпло-холод живёт между ключом и контровым, а не глобальным фильтром |
| «пусто сверху ИЛИ сбоку» | **долями кадра**: предмет в нижних двух третях, верхняя треть — тёмное негативное пространство (туда же кладёт буквы `paint_hook`) |
| «читается на 120 px» | «три-четыре тональных пятна, силуэт не разрывается, читается в grayscale на 120 px» |
| паттерн одной фразой | у каждого паттерна **размер плана, высота камеры, форма света** и чем он читается на 120 px |

**Свет намеренно живёт в паттерне, а не в общем каркасе.** У объекта в
упор и у общего плана с костром схема разная, и общая поверх частной их
бы столкнула — а конфликтующие световые указания измеримо роняют
предсказуемость.

Порядок частей внутри промпта тоже изменился: формат и паттерн стоят
первыми, потому что **xAI переписывает промпт перед генерацией**
(`revised_prompt`) и хвост «украшает» охотнее, чем начало.

## 4.3 Три правки вокруг промпта, без которых он бесполезен

**(1) Слова качества протекали через `scene_hints`.** Когда в
спецификации нет `youtube.cover_scenes` (а его нет у большинства
выпусков), сцена берётся из `image_prompts` — а те написаны под
иллюстрации ролика и начинаются с «Cinematic photoreal wide shot of…».
Эта приставка уезжала прямо в слот `SUBJECT` и включала тот самый
глянцевый режим. Замер на `gateway-process-01`: в промпт обложки
уходило «Cinematic photoreal wide shot of a weathered vintage 1983
declassified military document…».

Теперь `_clean_scene` срезает приставки цепочкой и вырезает чистые
прилагательные качества где угодно в строке. Проверено на всех пяти
боевых спецификациях.

**(2) `resolution: "2k"` в запросе к xAI.** Умолчание эндпойнта — `1k`, а
микрофактуре (зерно, халация, края букв) на `1k` негде жить. Обложка
весит мегабайты против полугигабайта у ролика — платить тут не за что.

**(3) Найден и починен настоящий баг в `xai_cover`.** На **любые** 400
повтор шёл сразу без `aspect_ratio` — а умолчание эндпойнта квадрат.
То есть «спасательный» заход молча отдавал обложку 1:1, которую никто
не ресайзил и никто не смотрел, и она уезжала на YouTube с полями.

Теперь параметры отбрасываются **по одному, от наименее важного**
(`resolution` → `aspect_ratio`), а скачанный кадр проверяется замером
пропорции (`_fix_aspect`) и при нужде режется по центру. Плюс
`revised_prompt` пишется в лог — это единственный способ увидеть, что
на самом деле ушло в диффузию.

## 4.4 Переключатель `TEXT_BY_MODEL` — и что я рекомендую

Добавлен флаг `covers.TEXT_BY_MODEL`. **Переключён на `False` по
решению автора:** модель отдаёт чистый кадр с тёмной полосой сверху
(`PLATE_LOCK`), а жёлтый Anton кладёт `paint_hook` — тот же код, что уже
работает в запасном пути без ключа. Оба режима проходят `self_check`.

**Почему `False`:**

- **Цифры.** На MARIO-Eval только **14.4%** сырых картинок Flux-стека
  (на нём стоит grok-imagine) воспроизводят запрошенный текст в
  точности. Для 3–5 слов успех держится примерно на 85% и разваливается
  дальше. `cover_texts` разрешает **до пяти слов**, то есть канал живёт
  ровно на границе.
- **Проверить опечатку здесь некому.** `build_covers` пишет файл,
  логирует килобайты и **кэширует** его: «уже есть, не трогаю». Никто не
  смотрит на пиксели. «THE 1983 CIA DOSSSIER» уедет на YouTube и
  останется там, пока человек не удалит jpg руками.
- **Бренд.** Протокол обложек требует: «менять кадр и хук; не менять
  буквы». Модель каждый раз рисует СВОИ буквы — другой вес, другой
  трекинг, другое место. PIL даёт побайтово одинаковый Anton и один и
  тот же `#FFD400` на всех выпусках.
- **Кегль.** `paint_hook` бинарным поиском гарантирует, что строка влезла
  в 92% ширины и 42% высоты — то есть физически обеспечивает высоту
  капители, которой требует protokol на 120 px. Модель этого не
  гарантирует.
- **Деньги.** Перегенерация из-за кривой буквы — оплаченная картинка и
  новый прогон. Перерисовка текста в PIL бесплатна и мгновенна: хук
  можно поменять без единого запроса к xAI.

**Контраргумент, и он честный:** текст, рождённый вместе с кадром,
«сидит» в сцене — уходит за объект, ловит свет; наложенная плашка
читается как наклейка, и зритель считывает это как низкое усилие.
Снимается это не рендером текста, а тем, что `PLATE_LOCK` просит **не
пустой прямоугольник, а тёмную малодетальную область, принадлежащую
сцене** (градиент неба, стена в тени, уход в чёрное) с яркостью ниже
25%. Мягкая тень под буквами в `paint_hook` уже есть.

**Переключать надо сразу на обе обложки и осознанно.** Половина выпуска
одними буквами, половина другими — хуже любого из двух вариантов.

**Следствие, которое пришлось починить в шаблоне.** У `ancient-example`
в `cover_prompts` был вписан `{text}` — то есть шаблон учил сценариста
просить у модели буквы. В режиме `False` это заставило бы её нарисовать
свои буквы ПОД нашими. Поле убрано целиком: `cover_scenes` +
`cover_patterns` там уже есть, и это теперь единственный правильный
способ задать кадр. `self_check` предупреждает, если хук всё-таки
остался в чьём-то `cover_prompts`.

## 4.5 Честный минус нового промпта

Промпт вырос с **240 до ~550 слов** (каркас 301 + паттерн ~80 + сцена +
`PLATE_LOCK` 155). А по тому же исследованию **длинный промпт ухудшает
рендер текста** на Flux-стеке.

**При `TEXT_BY_MODEL = False` этот минус не стоит ничего:** букв в кадре
нет вовсе, портить нечего, а длина работает только на подробность кадра.
Это, кстати, ещё один довод за выбранный режим — при рендере текста
моделью подробный кадр и надёжные буквы тянули бы в разные стороны, и
формулировками это не устраняется.

**Что проверить на первом же боевом прогоне:** открыть обе обложки и
посмотреть на верхнюю треть. Если модель насовала туда веток, бликов или
мелких предметов — жёлтый там читаться не будет, и лечится это усилением
`PLATE_LOCK`, а не правкой `paint_hook`.

## 4.6 Чего в правке НЕТ (сознательно)

- **Структура не тронута.** Картинка + текст, `paint_hook`, кэш готовых
  jpg, `thumbnail.jpg` = `cover_1.jpg`, вызов из `youtube.py` — всё как
  было.
- **Тексты хуков не тронуты.** `cover_texts`, `BANNED_HOOKS`, лимит в
  пять слов, приоритет `youtube.cover_texts` — без изменений.
- **OCR-проверки готовой обложки нет.** Она напрашивается (см. 4.4), но
  это уже новый механизм и новая зависимость, а не промпт-инжиниринг.
  Вынесено в предложения.

# ЧАСТЬ 5. ПРОИЗВОДСТВО, УСКОРЕНИЕ, ТЕХДОЛГ

## 5.1 Распараллелить склейку групп. **С / ускорение**

`join` крутится последовательно по ~20–25 группам, хотя `render_one`
перед этим занимал все ядра. Группы **независимы друг от друга** —
каждая пишет свой `seg_NNN.mp4`, единственная связь — флаги
`first`/`last`.

```python
with ThreadPoolExecutor(max_workers=max(1, cores() // 2)) as ex:
    ex.map(join_one, groups)
```

`max_workers = cores() // 2`, а не `cores()`: x264 сам многопоточный, и
запуск четырёх процессов на четырёх ядрах даст переподписку.

**Ожидаемый выигрыш:** этап склейки — примерно половина времени этапа 2.
При 4 ядрах и 2 параллельных процессах реалистично **−25–35% общего
времени монтажа**. Точная цифра — только замером.

**Риск:** память. Каждый процесс держит 12 декодеров + фильтр-граф.
На раннере 16 ГБ два процесса пройдут, четыре — под вопросом. Начинать с
двух.

## 5.2 Кэшировать группы, а не кадры. **С / ускорение пересборок**

`tmp/` не кэшируется, и `stage: render` перерендеривает всё. Кадры
кэшировать нельзя (десятки гигабайт), но **`seg_NNN.mp4` — это уже
сжатый финальный поток**, и весь их набор весит примерно столько же,
сколько `final.mp4`, то есть 400–600 МБ.

Не влезает в 10 ГБ на репозиторий при нескольких роликах — но **влезает
на один ролик**, и именно он пересобирается пять-десять раз подряд.
Предложение: отдельный кэш `segs-<id>-v1-` с ключом, включающим хэш
плана кадров (`shots.json`) и вектора стиля. План не изменился — группы
берутся готовыми, меняется только звук и сшивка. Пересборка ради правки
музыки или хвоста станет **минутами вместо часа**.

**Риск:** ключ обязан включать ВСЁ, что попадает в группу, — план,
LUT, оверлей, зерно, виньетку, список `moments`. Забыть одно поле —
получить ролик, собранный из старых групп с новыми титрами.
Это тот же класс, что `policy_key` в `vet_cache.json`, и делать надо по
его образцу.

## 5.3 Убрать двойное кодирование там, где оно бесплатно. **Н / ускорение**

`render_one` пишет промежуточные кадры с `crf 18`. Финал всё равно
давится до `crf 22`. Поднять промежуточный до `crf 20` — качество на
выходе не изменится (второй проход доминирует), файлы станут меньше
примерно на 30%, а значит быстрее пишутся и читаются.

Ещё дешевле: промежуточные кадры писать в `-c:v libx264 -preset
ultrafast -crf 16`. Файлы больше, но кодирование заметно быстрее, а
диск на раннере не узкое место. **Замерить оба варианта, выбрать по
факту.**

## 5.4 `noise` и `vignette` — посчитать, сколько они стоят. **Н**

Оба постоянные на весь ролик и оба покадровые на полный кадр. Есть
подозрение, что `noise` — самый дорогой фильтр графа после x264.
Если так, альтернатива: **готовый слой зерна как файл** (по образцу
`assets/overlays/`), накладываемый `blend=all_mode=overlay` — один
декодер вместо покадрового генератора. Сначала замер, потом решение.

## 5.5 Починить «переход последнего кадра группы». **С**

См. дефект (A). Это не оптимизация, это баг, и он бьёт по 2.2.
Отдельным пунктом здесь потому, что его надо делать ДО работ по главам.

## 5.6 Валидация верхнего уровня спецификации. **Н / 0**

По образцу `OVERRIDABLE` в `style_override`: закрытый список допустимых
ключей верхнего уровня `jobs/*.json`, неизвестный ключ (кроме
начинающихся с `_`) роняет смоук. Закрывает целый класс инцидентов,
который уже стоил роликов.

## 5.7 Общий модуль вместо копий. **Н / 0**

- `words_from_alignment` живёт в `shorts.py`, а нужна и акцентам (2.4),
  и потенциально `youtube.py`. Вынести в `pipeline/timing.py`.
- Разбиение на предложения продублировано трижды (`assets.sentence_marks`,
  `mock.split_sentences`, `youtube.first_sentence`) с одинаковым
  регулярным выражением на инициалы. В CLAUDE.md прямо написано, что
  они обязаны резать одинаково, — значит это одна функция в одном месте,
  а не три копии с комментарием «не забыть поправить все три».

## 5.8 Умнее подбирать футаж под смысл сцены. **С / 0**

Три правки, все бесплатные:

1. **Стемминг.** `monument`/`monuments`, `stone`/`stones` сейчас не
   пересекаются. Обрезка окончаний `-s/-es/-ing/-ed` на обеих сторонах
   даёт заметный прирост попаданий за десять строк. Никаких библиотек.
2. **Словарь синонимов темы в спецификации.** Новое поле
   `synonyms: {"guidestones": ["monument","granite","slab","stele"]}` —
   расширяет мешок слов файла при подборе, не трогая запросы к стоку.
   Пишет сценарист, он знает предметную область выпуска.
3. **Двухсловные сочетания.** Сейчас мешок слов одиночный, и «desert
   road» матчится с «road» чего угодно. Добавить биграммы с весом 3×
   к одиночным — «desert road» бьёт «road» без всяких порогов.

## 5.9 Разнообразие сценарной структуры

Слой `editorial` разводит МОНТАЖ и делает это хорошо. Текст не
разводится ничем, кроме протокола и человека. Что можно добавить
бесплатно:

- **записывать в `channel/log.json` форму структуры** (число глав, длину
  вступления, тип концовки, наличие «поворота» в середине) и проверять в
  `channel.check` — «третий ролик подряд с одинаковой семиглавой
  структурой»;
- **проверять открытие сценария на шаблон**: первые 150 знаков против
  первых 150 знаков последних восьми роликов. Если четыре из пяти
  открываются «I had watched…» — это ровно тот конвейер, за который
  YouTube снимает монетизацию;
- **держать в `ИНСТРУКЦИЯ-ЧАТ.md` список уже использованных
  структурных ходов** и требовать от сценариста новый. Механически это
  то же, что `avoid()` для цветокора, только для текста.

## 5.10 Прочие хвосты

- `magnific.py` — 897 строк мёртвого кода под флагом `MAGNIFIC_ENABLED

# ПОРЯДОК РАБОТ (предложение)

Волнами, каждая заканчивается прогоном смоука и одним боевым роликом.

**Волна 1 — то, что чинит уже сломанное (1–2 дня):**
5.5 (переход на границе группы) → 5.6 (валидация спецификации) →
2.2.1 (затемнение глав, зависит от 5.5) → 2.1.3 (кегль карточки).

**Волна 2 — удержание, дёшево (2–3 дня):**
2.1.2 (настоящая пауза под карточку) → 2.3 (гибридный финал) →
2.2.2/2.2.3 (стиль и номер главы) → 2.1.1 (динамика первых секунд).

**Волна 3 — шортсы (2–3 дня):**
3.3.1 (темп) → 3.3.4 (субтитры) → 3.3.5 (хук) → 3.3.3 (раскладка) →
3.3.8 (смоук) → 3.3.6 (монтаж из кусков, последним — он самый рискованный).

**Волна 4 — акценты (2 дня):**
5.7 (вынести `words_from_alignment`) → 2.4.1 (поле `accents`) →
2.4.2 (рисование) → 2.5 п.1 (пословный въезд).

**Волна 5 — производительность (1–2 дня, можно параллельно):**
5.3 (замер crf) → 5.4 (замер noise) → 5.1 (параллельная склейка) →
5.2 (кэш групп).

**Волна 6 — обложки:** Часть 4, отдельно от всего (не трогает монтаж).

**Волна 7 — подбор и структура:** 5.8, 5.9.

уже дважды приняты решения по замеру (zoompan 31×, порядок eq/curves), и
оба раза замер показал не то, что ожидалось.
